# Claude Code 実装指示：研究用・自然な吸気による自発的発話希望アバター

## 目的と合格ライン

**これは見た目だけのデモではない。** 人間1人とAIアバター1体が日本語で5分以上、ハンズフリーでリアルタイム音声対話を続けられるシステムを作る。人間が話している**途中**で、LLMが会話内容から独立した質問・確認・反論・提案の必要性を検出した場合、**発声する前に**アバターが自然な吸気を見せる。人間が続ければAIは待つ・発話内容を更新する・撤回する。発話機会が生じた場合は自然な音声で話す。相手が話し始めればAIは発話を中断できる。

研究上の狙いは、単なる操作可能性ではなく、参加者が「AI自身が言いたいことを持った」「発話を強要されず、相手として存在している」と実感できるかを**探索的に観察できる最低限の体験品質**の確保。信頼感・主体性・親密感の向上を実装で保証したと主張してはいけない。

既存ZIP `BREATH_LLM_Inhale_Avatar_Demo.zip` は概念と画面遷移の参考にとどめ、音声対話・発話制御・アニメーションを再設計する。既存コードのテストはサーバーの応答と模擬LLM結果に限り、音声・Gemini本番連携・実際の参加者体験を証明していない。

## 必須の挙動（参加者の目に映る流れ）

1. マイクの使用許可を得た後、研究者設定なしで日本語会話を開始できる。参加者に話すボタン、発話許可ボタン、手動の延期ボタン、文字起こし／LLMの内部意思表示を常時表示しない。
2. 参加者の発話が続いている間、STTの途中結果（最終結果待ちではない）を使って、内容依存の発話候補と理由をLLMが生成する。候補を出さないことも正常動作。発話内容を機械的な質問に限定しない。
3. 内容上「今言いたい」状態になったとき、アバターが自然な**準備吸気**をする。発話タイミングはVAP/発話状態と人間の反応を見て後から決める。`want_to_speak` と `allowed_to_speak` を混同しない。
4. 人間が続ければ、視覚的にしつこく合図を繰り返さず待つ。内容が更新された場合は候補発話を再評価し、陳腐化したら撤回する。人間から「どうぞ」「何かある？」等の発話促しがあれば、STTの文脈と音声状態の両方を参照して可能な範囲で応じる。音声だけで発話権の譲渡を確定的に知ったと表示しない。
5. AIの発話中も人間の音声を継続監視でき、明確な割り込みがあればTTSを停止／譲渡する。AI自身の音声が人間の入力として誤検出されないよう、別チャンネル・AEC・ヘッドホン推奨など対策する。
6. 発話後も会話は連続して再開する。毎回マイク開始を押し直さない。オンライン体験で話の途中の合図が遅れて届く場合は、その遅れを測定し再評価する。
7. アバターが単なるアニメーションに見えないこと。実用レベルの音声品質、吸気の立ち上がり／保持／解除、視線の協調、喋りに同期した口の動き、自然な待機・聴取姿勢を実装する。

## 推奨アーキテクチャ

```
音声マイク (WebRTC / AudioWorklet 等)
    ├── 低遅延・ストリーミングSTT → 途中文字起こし → LLM 意図判定器
    │                                                  ↓
    │                                           発話候補・理由・優先度・有効期限
    │                                                  ↓
    ├── MaAI/VAP 日本語リアルタイム推論 → 発話継続予測 →  発話交渉コントローラ
    │                                                  ↓
    │                                           idle → preparing_breath → holding
    │                                                  ↓         ↓       ↓
    │                                               speaking   defer   withdraw
    │                                                  ↓
    └── 人間の音声・介入検出 ←───────────── 低遅延TTS + 3Dアバターの発話動作
```

- Python側で公式 MaAI を動かし、Node.js/WebSocket等でブラウザと連携してよい。単一チャネルVAPで動かし始め、AI音声との競合が問題になったらユーザー・AIの2チャネル構成に移す。
- 公式資料： https://github.com/MaAI-Kyoto/MaAI と https://maai-kyoto.github.io/MaAI/ 。2026-11時点のREADMEでは `pip install maai`、単一入力例 `Maai(mode="vap",lang="jp",frame_rate=10,audio_ch1=mic,device="cpu")` 。実際の導入時は最新のREADMEとexampleでインストール・出力形式を再検証。
- VAPは**近い未来の発話活動**を推定する。発話する内容や、「人間が心理的に譲った」という意図の推定器ではない。閾値をひとつ決めて全状況に固定せず、実ログで誤開始・遅延を点検する。
- LLMの判断は「発話したい内容・根拠」、対話制御は「いつ合図を見せる／話す／待つ／取り消す」を管理する。1つの同期API呼び出しにすべてを任せない。
- 音声認識・VAP・TTSは非同期処理。古いLLM返答は発言時刻と入力発話のversionで検出して破棄／再評価する。
- 参加者側と研究者側の画面を明確に分離し、参加者側に内部状態・誘導的な評価ワードを出さない。

## アバター表現の要件

- Blenderでリグを調整したモデル、または利用許諾を確認したVRMモデルを使用。Three.js + `@pixiv/three-vrm` などでリアルタイムの骨格・表情制御を実装する。公式： https://github.com/pixiv/three-vrm
- **通常呼吸と、発話しようとして吸う準備吸気を明確に区別する**。発話意思がないときは目立たない安静呼吸。発話希望時は胸郭の膨張、鎖骨・肩の小さな挙上、頭頸部の軽微な姿勢変化、顔・口の準備、吸気後の保持／呼気への自然な復帰を協調させる。過剰な大げさ動作、風の線、発光、文字の吹き出しなどの視覚記号は使わない。
- 視線の協調はオプションで切り替え可能にし、**吸気そのものの効果**と混同しない。顎・眼球・まばたき・音声の口形は時系列に沿って同期させる。
- 胸郭動作が見えないVRMモデルなら、ボーン回転のみで自然に実現できたと主張せず、モデル側の専用リグ・blendshapeを追加する。
- 研究者が連続パラメータとして吸気の深さ、速度、保持時間、頭部姿勢を変更できること。計画的な録画比較ができる。
- 狙いは3Dの解像度ではなく、**発話前の意思が身体として自然に伝わること**。実参加者に「何の動作だと思ったか」を自由回答で聞く。事前に教え込んだ条件だけで解釈率を測らない。

## 研究用の比較・観測（初版は探索実験）

参加者に説明する前に「吸気を見たとき何を想像したか」を自由回答で聞けるようにする。会話の評価を見た目だけのアンケートに還元しない。

**初期比較可能な条件**（実装上の同一プラットフォームを確保）：

- `reactive`: ユーザーが話し終えた後に応答する（対照）。
- `initiative_no_cue`: LLMが内容依存の発話候補を保持するが、発話希望の身体的予告は表示しない。
- `initiative_inhale`: 同じLLM発話候補に身体的な吸気予告を追加し、人間の継続に合わせ延期・撤回する。

※一度に複数の変数が変化した比較から「吸気の因果効果」と言い切らない。最初は成立性／不自然さの発見に使い、厳密比較は条件整合を確保してから設計する。

**必要なログ**：セッションID、条件、マイク発話開始・終了、STT途中／確定文と時刻、LLMへの入力version・送信／受信時刻、発話候補・理由・判定、吸気開始／終了、VAP出力（時刻付き）、発話開始／終了、割り込み、延期・撤回、音声再生中断、誤起動、音声系エラー。可能ならオプトイン音声録音。あとから同時刻上に再生可能なイベントタイムラインを表示する。

## 受け入れテスト（見た目だけの完成報告は禁止）

1. **ハンズフリー**：一般的な日本語会話を5分以上継続。話す／待つためにボタン操作を要求しない（実験者モードは例外）。
2. **内容依存**：人間が2つ以上の異なる話題を説明し、内容に結びついた異なる発話候補を生成できる。重要でない発話で無理に介入しない。候補がユーザー発話途中で生成された時刻をログで確認できる。
3. **吸気の同期**：合図が発話候補の生成に対応して発生する。LLMの返答が遅延・陳腐化したときは古い理由のまま吸気しない。
4. **継続時の配慮**：合図が出た後、参加者が話し続ければ、AIは遮らずに保持・修正・撤回する。すぐに音声で割り込むような誤動作を記録する。
5. **譲渡・割り込み**：言葉で「どうぞ」「何か質問ある？」と言われたら、可能な範囲でそれに応答する。AI発声中に人間がはっきり話し始めた場合も適切に中断できることを確認する。
6. **本物のMaAI**：依存パッケージの実ロードとリアルタイム推論出力の実ログが存在し、VAPの値が実際の制御器に入力されていること。MaAI未稼働ならその状態を明示し、単なるRMS処理をVAPと呼ばない。
7. **自然さ**：吸気・保持・復帰の動作が滑らかで、音声・姿勢と矛盾しない。実際の会話を録画し、機械的なタイミングや不自然な静止がないか人間が評価できる。
8. **記録・再現性**：同じテスト会話をリプレイし、STT・LLM・VAP・アバター・TTSのタイムラインと遅延分布を表示できる。実測していない遅延や成功率を報告しない。
9. **障害時挙動**：STT/LLM/TTS/VAPのいずれかが落ちてもUIが黙って擬似結果を出すことなく、研究者に原因とデグレード状態を知らせる。

**完成報告の必須証拠**：起動コマンド、主要バージョン、APIとモデルの検証状態、動作シナリオの実ログ、VAP出力例、遅延測定値、正常系／失敗系のテスト結果、録画またはそれに相当する実演。自動テストだけで参加者にとって自然だと結論しない。

## 実装の優先順位

- P0: 生の音声を扱う全二重の連続入出力、ストリーミングSTT、LLMの内容依存の意思生成・キャンセル、音声TTSと人間割り込み対応。**ここが成立しないなら3D外見を磨かない**。
- P1: 発話希望の実際の時刻に同期したリグ付きアバターの自然な吸気・保持・解除、音声との同期。
- P2: 実際のMaAI/VAP推論を接続し、人間の発話継続／交替を扱うコントローラ、時刻付きログ。
- P3: 被験者モードの整備と自然さ・自発性知覚の小規模予備観察、必要なら追加モーションや条件の比較。

上位フェーズの受け入れテストを満たさない限り、次フェーズの完成を宣言しない。外部APIキーやモデル・資産の利用許諾が必要な場合は明示し、ユーザーの秘密情報をリポジトリにコミットしない。

## 既存版の問題（ソース実査）

- `public/app.js`: `scheduleAnalysis()` は1.2秒デバウンス、`analyzeText()` は前回から4秒かつ18文字の追加制約。LLMを同期的に待った後に吸気開始するため、発話中の適時性を保証しない。
- `public/app.js`: AIが話すときに `stopRecognitionForSpeech()` でSTTを停止。AIへのバーインと全二重音声対話が未成立。
- `public/app.js`: `tick()` のRMS／無音1700msは人間の譲渡意思を示さない。
- `public/index.html` と `public/styles.css`: SVGの2D変形・表示効果による吸気。3D胸郭のリグ操作、口形同期、連続的な呼吸制御はない。
- `server.mjs`: Gemini `generateContent` に部分文字起こしを送るだけの単発HTTP方式。動作するAPIキーでの本番通信や音声ストリーミング統合は既存テストでは検証されていない。

## 最終的な研究上の注意

これが完成しても「自発的なAIは独立して感じられ、信頼と親密さが上がる」という仮説は未検証のまま。実装段階の目標は**その仮説を、人間の対話体験を壊さず確かめられる装置を作ること**。
