## 2. 差分と修正

### 2.1 条件間の不一致

**修正前の差。** `initiative_no_cue` は `WAIT_FOR_TURN_END` の候補を話した。持ち越し、応答の材料、吸気中の開始の保留がなかった。合図を待たずに話せたので、発話の時刻も内容も吸気の条件と違った。

**修正。** `initiative_no_cue` も同じ状態遷移、ゲート、冷却時間、吸気と保持の時間、延期、WAIT の扱いを通す（影の合図）。違いは提示だけで、`breath.*` と `signal.*` を送らない。`reactive` と TurnManager は変えていない。

**記録。** 状態名は共通なので、`BREATH_*` は提示を意味しない。提示の有無は次で分かる。

- `manifest.initiative.cue_presentation`
- `negotiation.decision` の結果 `shadow_cue`、`shadow_release`、理由 `not_presented:initiative_no_cue`
- `cue_id` の接頭辞 `shadow_`
- `negotiation.cue_reaction.cue_presented`

`tools/log_check` は `initiative_no_cue` のログに `signal.*` があると失敗する。

**残る違い（提示そのもの）。** 吸気、保持、脱力の動き、息の音、発話の開始時の解除、延期からの短い準備動作。`initiative_no_cue` には代わりの動きを足していない。

### 2.2 合図の後の反応の反映

**修正前。** `negotiation.cue_reaction` はログだけで、判定は合図を出したことも、その後の人の様子も知らなかった。

**修正。** 発話希望の判定に、候補ごとの事実を渡す（`initiative-desire-ja-v4`、`cognition/initiative/offer_view.ts`）。

- 提示：`presented`（ブラウザが描画を報告）、`sent_unconfirmed`、`not_presented`
- 経過秒数
- その後の人の様子：話し続けている、止まった、促す語句を言った、不明

**規則。** 話し続けることは拒否でも無関心でもない。人は合図を見ていないかもしれない。KEEP、REVISE、WITHDRAW は実際に話された内容で選び、合図の有無や人の振る舞いだけを理由にしない。WITHDRAW はこれまでどおり発話の根拠が必須で、ゲートが確認する。NEW の指示と回数に関わる言い回しは変えていない。

**記録。** 判定に渡した内容は `initiative.desire.offer_views` に残す。

**限界。** REVISE を反応だけで選ばないことはプロンプトの規則に依存する。`stopped` は tick ごとの値で、短い途切れも含む。文字の増えない反応の変化では判定を起動しない（内容の判定は KEEP しかありえず、2 回の LLM は許可の後に届くため）。

### 2.3 時間軸

- `signal.started` が `signal.sent` より前になる例のうち、-2770 ms は分析側の対応づけの誤り（`relax` は合図ごとに 2 回送られる）でバグではない。
- -978〜-1321 ms は、すでに修正済みの `timeOrigin` のずれで、修正前のログである。
- **-1〜-81 ms は実際の不具合だった。** 起動直後の軸の推定の偏りが、時計差の推定に残っていた。Worker の時計で測った値と軸を報告のたびに合成するように直した。値の丸めはしていない。
- 修正後の実 API の 2 セッションでは、異常の疑いが 0 件だった（送信から描画まで 6〜92 ms、4 件）。

詳細は `docs/time_axes.md`。

## 3. 遅延の実測

**条件。** 実 STT、Gemini、ElevenLabs。話者は合成音声（33 秒と 25 秒の長い発話、内容は架空）。2 セッション、各 72 秒。**人の声ではない。**

| 区間 | 中央値 | 件数 |
|---|---|---|
| 音声 → ASR の受信（推定） | 229 ms | 4 |
| ASR に根拠が出てから判定の送信まで | 593 ms（136〜4015） | 4 |
| 発話希望の LLM | 1297 ms | 4 |
| タイミングの LLM（llm 方式のみ） | 1320 ms | 1 |
| 判定 → `signal.sent` | 8 ms | 4 |
| `signal.sent` → 描画 | 58 ms | 4 |
| **話された語 → 吸気の描画（推定）** | **2778 ms**（1703〜5845） | 4 |

- 描画の時点で話の途中だったのは **4 件中 4 件**。計測できた 2 件では、その後 4.6 秒と 25.3 秒話し続けていた。
- 短い合成の文（前回）では 5 件中 4 件が話の途中だったが、その後は 0.2〜2 秒で途切れていた。**話の途中に届くかは、話の長さに強く依存する。**
- 判定の送信までの待ちが最大 4 秒になる例があった。前の判定が実行中だった可能性があるが、原因は未確認である。

**遅延の改善の判断。** 長い発話では話の途中に届いているので、今は実装を変えない。人の声で測ってから、次の順で検討する。

1. 判定の待ちの原因の調査
2. タイミング判定の並列化（llm 方式の約 1.3 秒）
3. interim の段階での先行判定

## 4. 発話希望の内容の観察（評価ではない）

上の 2 セッションのログを読んだ印象であり、評定はしていない。

- 発話希望は NEW 7、KEEP 9、WITHDRAW 2 だった。1 セッションあたり 3〜4 件の候補である。
- `QUESTION` が大半で、「どのあたりを想定しているか」のように、**話し手がこの後すぐ話しそうなことを尋ねる候補**が目立った。実際に次の文で話され、撤回になった例がある。
- 話の中の矛盾（「電車で通える範囲」と「高崎」）を指摘する候補は生じなかった。
- ASR の誤り（高崎 → 高き）がそのまま理由に現れている。
- 「発話希望が意味を持つか」は、条件を知らない 2 名の評定が必要である。プロンプトはその結果を見てから変える。

## 5. 人の声での確認の手順（本人の声のみ）

1. `docs/runbook.md` §9 のとおりにサーバーを起動する。
2. `?condition=initiative_inhale&conversation_kind=joint_thinking&timing_strategy=immediate` で開く（`timing_strategy=llm` でも 1 回）。
3. ヘッドセットで、20 秒以上続く話を 3 分ほど話す。
4. `npm run latency:initiative -- sessions/<id>` で区間別の遅延と話の途中かどうかを見る。
5. `npm run review:initiative` で候補の内容を確認する。
