### 計画 §4.1 への帰結

**`p_now_ai = p_now[1]`、`p_future_ai = p_future[1]`、`user_speaking` は `vad[0]`、`system_speaking` は `vad[1]` で確定できます。** HRI 2025 の擬似コードの「p = ロボット側」と一致する配線です。README の例（`[0.87, 0.13]` は話者1が次の話者）とも一致します。

### 向きとは別に、制御に効く挙動

- **無音で値が保持される。** 長い無音に入っても p はすぐ 0.5 に戻りません。ch2 の発話の後の無音（50-55秒）で `p_now[1]`=0.94、最後の ch2 の後（95-100秒）では 0.19 と、無音の前の内容で大きく変わります。**AI が話し終えた直後の `p_now[1]` の高さを「AI に発話権がある」根拠に使わないでください。**
- **話者のポーズで相手側の p が上がる。** ch2 をゼロのままでも、ch1 のポーズ中に `p_now[1]` が 0.5 を超えます（下表）。
- **話者交替の周辺**（素材そのまま。ch1→ch2 14件、ch2→ch1 32件の平均）。次の話者の `p_now` は発話開始（エネルギー基準）の約 0.24 秒前に 0.56〜0.58、開始後 0.08 秒で 0.81〜0.82 です。`p_future` の変化は小さく（ch2→ch1 は 0.40〜0.41 で、開始前後でほぼ動きません）、事象数も少ないので参考値です。

## 2. `process(x1, x2)` の直接呼び出し

`start()` なしで、`Maai.process` を1スレッドから呼びます（`probe_direct_process.py`、素材は `jpn_mix` 先頭30秒）。

| 確認 | `normal-ver2` 12.5Hz | `normal` 10Hz |
|---|---|---|
| `start()`＋`Chunk` 経路との差（`p_now` の最大絶対差） | **0.0**（374件） | **0.0**（300件） |
| 同じ音声の再実行（`reset_runtime_state()` 後）との差 | 0.0 | 0.0 |
| 別スレッドから呼んだときの差 | 0.0 | 0.0 |
| 1 frame のサンプル数 | 1280 | 1600 |
| 320 サンプル送信の呼び出し回数／frame | **4** | **5** |
| **最初の結果の `end_sample`** | **2560**（最初の出力を破棄） | **1600**（破棄なし） |
| 以降の結果 | 1280 ごと | 1600 ごと |
| 結果の `x1`、`x2` と入力 | `audio[end-1280:end]` と完全一致 | `audio[end-1600:end]` と完全一致 |

**番号の対応規則:** `process` に渡した累計サンプル数を自分で数え、その呼び出しでキューから出た結果に与えれば `audio_frame`（＝`end_sample`）になります。`t` は壁時計で番号ではありません。

**因果性（先読みなし）:** k サンプル目以降を変えると、値が変わるのは `end_sample > k` の結果からで、それ以前は完全に不変です（3地点で確認）。

**送信単位:**

| 送信単位 | 12.5Hz（Mimi） | 10Hz（CPC） |
|---|---|---|
| 160、320 | 値は同一 | 値は同一 |
| 640 | 値は同一 | 約数でない。frame が 1920 に伸びる（250件）。例外なし |
| frame と同じ | 値は同一 | 値は同一 |
| 480、512、1000（約数でない） | **`ValueError`**（入力長の不一致） | frame が伸びる（1920、2048、2000）。例外なし |

**誤用時の挙動（ワーカー側で防ぐこと）:**

- x1 と x2 の長さが違うと例外になります（Mimi `ValueError`／CPC `RuntimeError`）。**その後は次の呼び出しも失敗します**（Mimi `ValueError`／CPC `IndexError`）。`reset_runtime_state()` で戻り、戻った後の値は基準と差 0.0 です。
- **int16 のまま渡すと例外なしで誤った値になります**（5秒で `vad` 平均が Mimi [0.62, 0.79]、NaN なし）。Float32 への変換と正規化の確認が必要です。
- `process` は約100 frame ごとに性能行を、ロード時に警告を **stdout へ print** します。ロード時の `Parameter ... was not updated from its initial value` の警告（`*.mha.m`、`objective.codebook.emb.weight`）は全構成で出ます。影響は**未確認**です。
- 結果は無制限の `result_dict_queue` に入ります。呼び出しごとに `get_nowait()` で取り切ってください。

**`start()` の問題の再現:** `qsize()>100` の消去は実際に起き、背圧なしで30秒分を一度に入れると結果は 0〜1 件でした（警告はチャネルごとに出ます）。`start()` を使わない判断は妥当です。

**実測遅延**（最後のサンプルが揃う期限から結果が得られるまで。5.5分の実時間試験、推奨構成。§6 の表の `result_latency`）: **描画なしで p50 37.3 ms／p95 50.5 ms／最大 139.9 ms。** これは **`process` だけの値**で、WS、ブラウザ、Worklet の遅延は含みません（未測定）。音声の先頭から見ると frame の蓄積（12.5Hz で最大 80 ms）が足されます。

### 推奨と理由

**`jp_kyoto`／`normal-ver2`／12.5Hz／`mc=True`。**

1. **`normal`（CPC）は採用しません。** RTF は半分以下と速いのですが、**ゼロ埋めのチャネルで `vad[1]` が 0.33〜0.62 を示します**。AI が黙っている間も `system_speaking` が誤り、p も偏ります（ch2=0 で ch1 が黙っているとき `p_now[1]` > 0.5 が 0.61〜0.96）。§3.3 の「無音はゼロ埋め」と相性が悪い構成です。計画 §1.1 の観察（約 0.46）を、長い素材で確認しました。
2. **`jp_kyoto` と `jp`（どちらも `normal-ver2`）で RTF とメモリに有意な差はありません。** 差が出たのはターンの終わりの反応で、上の表のとおり `jp_kyoto` が大きく、ターンの終わりとポーズの分離（AUC）も少し良い結果でした。ただし素材1会話での差で、素材の偏りも否定できません。
3. **ライセンスの面でも `jp_kyoto`（MIT）は扱いが単純です。** 利用区分は非営利と確定したので `jp` も選べますが、推奨の根拠は上の測定で、ライセンスは決め手にしていません。
4. **`jp` だけの利点は 1ch の重みです。** 2ch を使う本計画では不要ですが、1ch の比較をするなら `jp` が必要です。1ch は RTF が約半分で、p はスカラーかつ正規化なしなので、2ch のしきい値は流用できません。
5. **`mc` は暫定です。** `mc=True` は README の既定で、雑音に強い学習と説明されています。ポーズでの誤反応は `mc=False` より少なく、ターンの終わりの反応も小さいという結果でした。**素材はほぼ無雑音で、雑音下の比較は未測定です。** 切替は引数1つなので、G1 の実マイクで比較してください。

**frame_rate:** `normal-ver2` は 12.5Hz のみです（重みの一覧と README）。比較対象の `normal` は 10Hz で測りました。

`jp_kyoto`／`normal-ver2`／`mc=True`、`jpn_mix` 先頭90秒、t=40秒から。回復＝`p_now[0]` の基準との差が 0.05 未満で1秒続くまで。

## 6. G0 負荷試験

**条件:** `probe_soak.py`。`jp_kyoto`／`normal-ver2`／`mc=True`。`jpn_mix`（265.7秒）→`eng_mix` の**連結**を実時間で 330 秒（5.5分）。**連続した1会話ではなく、英語も含みます。** 1スレッドで 20ms の期限に合わせて `process` を呼びます。

- `backlog` はチャンクの到着期限からの遅れで、受信キューの滞留に相当します。WS の受信スレッドは含みません。
- **他レーンが同時に動いており**（load average 5〜20）、専有環境の値ではありません。
- 描画は `load_page/`（Three.js 0.180 で `Sendagaya_Shino.vrm` を glTF として読み、3.2万三角形、148 ボーン、モーフを毎フレーム更新、1280×720、影あり）を Playwright Chromium の SwiftShader で実行します。three-vrm のスプリングボーン、AudioWorklet、WS は含みません。
- **ソフトウェア描画は CPU で全ピクセルを処理するので、実機の GPU 描画よりはるかに重い負荷です。** 全コアがほぼ飽和します。また本番の Chrome は Windows 側で動く想定で、この試験（どちらも WSL 内）と構成が違います。

| 条件 | スレッド torch/ONNX | RTF p50 | **RTF p95** | RTF p99 | 超過 frame（/4124） | backlog p50 / p95 / 最大 ms | 結果遅延 p50 / p95 / 最大 ms | 全体の使用コア | 描画 fps |
|---|---|---|---|---|---|---|---|---|---|
| **描画なし** | 4/4 | 0.460 | **0.586** | 1.29 | 72 | 0.6 / 23 / 120 | **37.3 / 50.5 / 139.9** | 5.4 | — |
| 描画あり | 4/4 | 0.889 | **1.713** | 2.29 | 1449 | 640 / 1621 / 2060 | 693 / 1669 / 2080 | 15.1 | 10.9 |
| 描画あり、320×180 | 4/4 | 0.911 | **1.685** | 2.37 | 1632 | 1354 / 8875 / 9472 | 1413 / 8926 / 9492 | 15.2 | 29.1 |
| 描画あり、コア固定（描画 12-15、ワーカー 0-7） | 4/4 | 1.203 | **1.939** | 3.03 | 2679 | 64114 / 92276 / 95070 | 64168 / 92330 / 95090 | 9.7 | 7.6 |
| **描画あり、ブラウザ `nice 15`** | 4/4 | 0.599 | **0.750** | 0.93 | 26 | 3.4 / 33 / 236 | 48.3 / 61.1 / 255.5 | 14.4 | 14.8 |
| 描画あり、ブラウザ `nice 15` | 2/2 | 0.685 | **0.816** | 0.92 | 14 | 8.3 / 40 / 104 | 55.1 / 66.1 / 124.4 | 14.0 | 16.3 |

全条件で結果数は期待どおり（4124/4124）、NaN なし、RSS は最初の1分で 694→725 MB、以後 729 MB で頭打ち（`ru_maxrss` の 696 MiB と同じ量）。描画なしの p95 は前半 0.563、後半 0.617 でした。

### 読み方

- **描画なしは暫定基準を満たします。** 滞留は最大 120 ms で、末尾10秒の最大は 34 ms と解消しています。ただし p99 は 1.29 で、1.7%の frame が予算を超えました。他レーンの影響か本質かは切り分けていません。
- **CPU が飽和すると基準を満たしません**（p95 1.7〜1.9）。優先度を与えない構成では滞留が数秒〜90秒に達しました。`process` だけでは解消せず、**§3.3 の過負荷時の同時破棄が必須です。**
- **コア固定は改善しませんでした。** 8論理コアに torch 4＋ONNX 4 を置いたうえ、他レーンのプロセスは固定していないので、0-7 にも重なったと考えられます。固定が一般に悪いという結論ではありません。
- **320×180 にしても飽和しました。** 解像度を下げた分 fps が上がり、rAF が空いた CPU を使い切るためです。低解像度なら軽いという根拠にはなりません。
- **ブラウザの優先度を下げると滞留は解消します**（p95 0.75、backlog p95 33 ms、遅延 p95 61 ms）。飽和下で基準 0.7 をわずかに超えるものの、持続する滞留はありません。
- **実機（GPU 描画、Windows 側 Chrome、WSL のワーカー）は未測定です。** Windows 側と WSL の間で優先度が効くかも未確認です。

## 8. 計画への修正提案

1. **§4.1:** 向きの仮置きを確定に変更（§1）。`system_speaking` も `vad[1]` でよい（`normal-ver2` に限る）。
2. **§4.1 の校正:** `p_now[1]` の 0.5 超えは重みと mc で大きく変わります（§4）。`policy.ja.json` は重みごとに校正し、AI 発話の直後は p が高いまま残るので除外を検討してください。
3. **§3.3:** 次を B レーンの要件に追加してください。frame は 1280 の倍数で破棄すると格子を保てる／例外の後は `reset_runtime_state()` と助走／長さの一致とデータ型の検査（int16 は例外にならない）／`result_dict_queue` を毎回取り切る／stdout の print を RPC へ混ぜない／ロード後に `variant` を検査。
4. **§3.3 の過負荷:** `backlog` の上限を決めて破棄を実装してください（飽和時は滞留が 90 秒に達しました）。上限値は未測定です。
5. **§3.2 の送信単位:** 20ms（320）は両方の frame の約数で問題ありません。ただし Mimi は約数でないと例外です。
6. **§5.3 G0:** 「ブラウザ描画を同時に動かした負荷」を WSL 内のソフトウェア描画で判定するのは不適当です。実機 GPU の測定を G1 の入口に移すことを提案します。基準 0.7 の妥当性も実機の値で見直してください。
7. **§4.1 の復帰の助走（10秒【暫定】）:** リセット直後の p は無音時に 0.5 付近から動きます。助走の長さの妥当性は未測定です。
8. **§8 のリスク:** CPU 飽和時の VAP の滞留を追加してください。`.venv` を作り直す際の lock に、probes の依存（`jsonschema`、`soundfile`、`pytest`、`matplotlib`）を含めてください。
9. **§1.2:** ピーク RSS は約 730 MB で、9GB の環境では問題ありません。
