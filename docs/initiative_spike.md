# 第1部: 録音のお願い

## 何をするのか

AI が「人の話の途中で、今、口を挟みたい」と判断してよい場面かどうかを確かめるために、台本を読み上げた音声を録音します。音声を Google の音声認識に通し、その結果を時刻どおりに AI の判定へ流します。

**読み間違いや言い直しは、そのままで構いません。** 認識の揺れも含めて試したいので、上手に読む必要はありません。

## 用意するもの

- Windows の PC と、静かな部屋。
- マイク。ヘッドセットがあれば、それを使ってください。なければ PC のマイクで構いません。
- 時間: 全部で 30 分ほど。

音声は自分の声だけにしてください。ほかの人に読んでもらう場合は、録音を Google へ送ることの了解を取ってください。録音ファイルの置き場 `recordings/` は git に入りません。

## 手順 1: 録音する

1. スタートメニューで「サウンド レコーダー」を開きます。
2. 右上の「…」から「設定」を開き、「録音形式」を **WAV** にします（ここが m4a のままだと、次の確認で止まります）。画面の名前は Windows の版で多少違うことがあります。WAV を選べないときは、無料の Audacity で録音し、「WAV（Microsoft）16-bit PCM」で書き出してください。
3. 下の台本を1本ずつ録音します。**1本につき1ファイルです。** 読み始める前と読み終えた後に、2秒ほど無音を入れてください。
4. 途中で大きく詰まったら、その1本だけ録り直して構いません。

**必ず録るもの:** C1、C2、C3、C4、C5、C6（反例の6種）

**できれば録るもの:** V1、V2、V3、V4（反例に合わせ込みすぎていないかを見る検証用）

## 手順 2: ファイルを置く

1. エクスプローラーのアドレス欄に次を貼り付けて開きます（なければ手順 3 を一度実行すると作られます）。

   ```
   \\wsl.localhost\Ubuntu\home\yuuto\projects\LLM_VAP_DEMO\recordings\initiative
   ```

2. 録音したファイルをここへコピーし、**台本の番号に名前を変えます。** 例: `C1.wav`、`C2.wav`、`V1.wav`。

## 手順 3: 録音を確認する（料金はかかりません）

WSL のターミナルで次を実行します。

```bash
cd ~/projects/LLM_VAP_DEMO
bash tools/initiative_spike/run.sh check
```

各ファイルの行頭の印を見てください。

| 印 | 意味 | すること |
|---|---|---|
| ○ | 問題なし | なし |
| △ | 長さが想定と違う | 途中で切れていないか聞き直す |
| × | 読めない、または名前が違う | 表示の案内のとおりに直す |

## 手順 4: 音声認識に通す（少額の料金がかかります）

```bash
bash tools/initiative_spike/run.sh transcribe --yes
```

- 録音の長さと同じだけ時間がかかります（10 本で 7 分ほど）。これは実時間で流す決まりなので、故障ではありません。
- 料金の目安は全部で $0.15 以下です（標準料金 $0.016/分 の場合）。`--yes` を付けないと、料金の目安だけを表示して止まります。
- 認識結果が画面に出ます。台本と違っていても構いません。
- 取り直したときは、`--take 2` を付けます。`--only C2` で1本だけ処理できます。

## 手順 5: C3 に誤認を入れる

C3 は「音声認識が途中で数字を聞き間違えた」場面を試します。都合よく間違えてくれるとは限らないので、録音の認識結果に、時刻を保ったまま人工的に誤認を入れます。

```bash
bash tools/initiative_spike/run.sh inject
```

「見つかりません」と出たら、手順 4 の画面で「五十万円」がどう書かれているかを見て（例: `50万円`）、次のように指定します。

```bash
bash tools/initiative_spike/run.sh inject --correct 50万円 --wrong 5000万円
```

## 手順 6: 評価する

`fixtures/initiative/runs/<名前>/eval.csv` を Excel で開きます。AI の判定が1行に1つあります。**右端の3列を別々に**埋めてください。

| 列 | 見ること | 例 |
|---|---|---|
| 内容の妥当性 | 言おうとした内容そのものは、的を射ているか | 指摘は正しいか |
| 今申し出る必要性 | 話し終わりを待たず、今申し出る必要があったか | 待っても同じなら「不要」 |
| 待機・撤回の妥当性 | 黙っていた（NONE）、または取り下げた（WITHDRAW）判断は妥当か | 本人が解消した後に取り下げたか |

値は「適切／不適切／判断できない」でお願いします。「理由（モデル出力）」の列は AI が書いた説明で、正解でも AI の本当の動機でもありません。文章がもっともらしいことで「適切」にしないでください。

## 台本

普段の話し方で、少しくだけて読んでください。

### C1: 長いが、言う価値のない説明

読み方: 思い出話のように、のんびり話してください。

> 去年の展示会のことなんですけど、えーと、場所は幕張で、駅からけっこう歩くんですよね。海の近くだから風が強くて、朝なんかはちょっと寒いくらいでした。
>
> お昼は会場の中のフードコートで食べたんですけど、カレーがわりとおいしくて、二日続けて同じのを食べちゃいました。ほかの会社のブースもいろいろ見て回って、なんか最近は大きいモニターを置いてるところが多いなあって思いましたね。
>
> 帰りの電車はどこも混んでて、ずっと立ってたので、さすがに足が疲れました。まあ、でも全体としては楽しかったです。

### C2: 途中で疑問が生じるが、数秒後に本人が解消する

読み方: 「足りないんですけど」の後、途切れずに続けてください。

> 来月の展示会のブース設営なんですけど、業者さんの見積もりが三十五万円で来てて、うちの設営の予算って二十万円なんですよ。だから十五万円足りないんですけど、まあ、それでもこの業者さんでいきたいなと思ってて、内装の感じがすごくいいので。
>
> あ、で、その足りない分なんですけど、先週部長に相談して、広報の予算から十五万円回してもらえることになったんです。なので設営はこのまま進められます。
>
> あとはパネルの原稿をいつまでに出すかですね。これは業者さんに来週聞いてみます。

### C3: 途中の音声認識の誤認だけで矛盾が見える

読み方: 数字は普通にはっきり読んでください。誤認は起きないこともあります。起きなければ手順の「誤認の注入」を使います。

> 今回の展示会の費用を整理してたんですけど、全体の予算が百万円で、そのうち出展料が五十万円なんですね。で、残りの五十万円で、ブースの装飾とパンフレットの印刷をやろうと思ってます。
>
> 装飾が三十万円くらいで、印刷が十五万円くらいなので、だいたい収まりそうです。当日の交通費はまた別で、会社の出張費から出ることになってるので、ここには入れてません。
>
> ということで、費用のほうはいったんこれで進めようかなと思います。

### C4: 重要な異議はあるが、話し終わってからで十分

読み方: 落ち着いた調子で、案を説明するように話してください。

> 当日の体制なんですけど、今のところの案としては、三日間ずっと僕一人でブースに立とうかなと思ってるんです。うちは人が少ないし、ほかの部署に交代を頼むのも悪いので。
>
> お昼は、まあ、来場者が少ない時間に抜ければいいかなと。説明の資料は机の上に置いておいて、自由に持っていってもらう感じで。
>
> まだ決めたわけじゃなくて、あくまで案の一つなんですけど、来週の打ち合わせでみんなに聞いてみようと思ってます。

### C5: 吸気の後も人間が話し続ける（G3 の素材。今回の比較の対象外）

読み方: 最後まで間を空けず、相手の反応を待たないつもりで話し続けてください。

> で、会場の予約なんですけど、あれ、十月の二十日までしか押さえてなくて、なのに搬入は二十一日にしようと思ってるんですよね。それで搬入のトラックは二十一日の朝一番で頼んで、ドライバーさんにも伝えてあって、荷物はパネルが六枚と机が二つと、あと椅子が四脚で、パンフレットが段ボールで三箱くらいかな。
>
> で、パネルは前の日に会社で確認して、机は向こうで借りられるかもしれないので、それも聞いてみて、椅子はたぶん足りるんですけど、一応多めに積んでおいて、それから延長コードと、モニターの台も要るんですよね。

### C6: 役割・関心と無関係な話題

読み方: 雑談のように話してください。

> そういえば週末に子どもと釣りに行ったんですよ。朝五時に起きて、車で一時間くらいの堤防まで行って。最初は全然釣れなくて、子どもが飽きちゃって、もう帰ろうよって言い出したんですけど。
>
> お昼前になって急にアジがかかり始めて、結局十匹くらい釣れたんです。帰ってから自分でさばいて、唐揚げにしたら、子どもが喜んで全部食べちゃって。
>
> 次は船にも乗ってみたいって言うので、夏休みにどこか探してみようかなと思ってます。

### V1: 誤った前提の上に計画を積み上げ、行動に移ろうとしている

読み方: 自信を持って、どんどん先へ進む調子で話してください。

> パンフレットの段取りなんですけど、展示会の開催が十一月の十二日からじゃないですか。で、印刷に二週間かかるって言われてるので、印刷に出すのは十二月の頭で間に合うんですよね。
>
> そこから逆算して、原稿の締切は十一月の末にしようと思ってます。写真の撮影は十一月の中旬で、デザイナーさんにも十一月末の入稿でお願いしますって伝えるつもりです。
>
> このあと、もうすぐ、この日程でメールを全員に送っちゃいますね。デザイナーさんの予定も、それで押さえてもらおうと思います。

### V2: 指示対象が分からず、続きの説明を理解できない

読み方: 相手が事情を知っている前提で、さらっと話してください。

> 例の件なんですけど、あれ、先方がだめだって言ってきたんですよ。なので、あっちの案に切り替えようと思ってて。そうすると費用がその分だけ増えるんですけど、それはこの前の話のとおりあそこから出してもらって、担当もあの人に変えれば、たぶん回ると思うんです。
>
> で、それに合わせて、来週のやつも前倒しにして、向こうにはこっちから連絡しておきます。日程がきつくなるので、準備は今日から始めたほうがよさそうです。

### V3: 筋の通った計画を順に説明している

読み方: 普通に報告するように話してください。

> パンフレットの段取りなんですけど、展示会の開催が十一月の十二日で、印刷に二週間かかるので、十月の二十日に入稿すれば余裕があります。原稿の締切は十月の十日にしました。
>
> デザイナーさんには先週確認を取ってあって、その日程で大丈夫と言ってもらってます。費用は十五万円で、予算の中に収まってます。
>
> 写真の撮影は九月の末に済ませる予定で、カメラは広報の山田さんが担当してくれることになりました。部数は千部で、去年の余りも少しあるので足りると思います。

### V4: 食い違いに気づかず話し、十数秒後に本人が訂正する

読み方: 「あ、すみません」の前まで、間違いに気づかないつもりで話してください。

> パンフレットの段取りなんですけど、展示会の開催が十一月の十二日で、印刷に二週間かかるので、印刷に出すのは十二月の頭にしようと思ってて、で、原稿の締切はその一週間前にして、写真もそれまでに撮ってもらって。
>
> あ、すみません、違う違う、十二月じゃなくて十月の頭でした。開催が十一月なので、十月の頭に印刷に出して、原稿は九月の末ですね。
>
> で、デザイナーさんには、その日程で来週お願いしようと思ってます。費用は去年と同じくらいで収まりそうです。

## 予備調査の結果

- 条件: `fixtures/initiative/runs/` の `p1_v1_tune`（版 `initiative-ja-v1`）、`p2_v2_tune` と `p3_v2_repeat`（版 `initiative-ja-v2`）。Gemini の呼び出しは合計 200 回（上限ちょうど。`call_ledger.json`）。失敗 0、JSON の不正 0。
- 実時間で流した。呼び出しを抑えるため、起動の条件は新規安定 40 文字または final（コードの既定 24／12 文字は未検証）。判定の間隔は約 5〜8 秒で、実運用より粗い。
- `flash-lite` は `thinking_level: minimal`、`3.8-flash` は `low`。Interactions API、`store: false`。
- 値は実行回数が少なく（各 n=1、V2 と V4 のみ n=2）、差の検定はしていない。「一致」は設計上の仮説（`scenarios.ja.json` の `expected`）との機械的な比較で、正解との比較ではない。

### 版 v1 と v2（プロンプトの効き方）

| 台本（各 n=1） | v1 flash-lite | v1 3.8-flash | v2 |
|---|---|---|---|
| C2 | NEW → WITHDRAW | NEW → WITHDRAW | 両モデル NONE |
| C4 | **NEW（残る）** | **NEW**、後で WITHDRAW | 両モデル NONE |
| V1 | NEW | NEW | 両モデル NEW |

v1 では両モデルとも「話が先へ進んでしまう」を待つ不利益として書き、案への意見でも NEW を出した。**モデルの差よりプロンプトの差が大きかった。** v2 は待つ不利益を確かめられる場合に絞った。逆に、v2 は NEW を出しにくくした分、V2 や V4 の見逃しを生んでいる可能性がある。

### 「40/40 件 NONE」は見逃しか慎重さか

- **flash-lite が常に NONE を返すわけではない。** 同じモデルが V1、V2、H1 で NEW を返した。
- 慎重さと読める例がある: V4 で flash-lite は理由の欄に「月が食い違っている」と書きながら「自分で訂正する可能性が高い」として NONE にした（理由の欄はモデルの説明であり、動機の証拠ではない）。3.8-flash も V2 で同様に NONE を返す。
- ただしプローブの仮のプロンプトと文をそのまま再実行していないので、40/40 の原因（プロンプトか、途中で切れた入力か）は切り分けていない。

### 目についた質の問題（件数は少ない）

- flash-lite の出力に、版 v1 で中国語の字（「12月头」「无人」）、版 v2 で理由の欄の読み違い（「十二月十二日開催」）があった。発話案が TTS へ行くなら確認が要る。v2 に表記の指示を足したが、効果は未確認。
- モデルの NEW がゲートで棄却された例は 0 件（全要求）。根拠の抜き出しは正確だった。ゲートの棄却は test double でしか通っていない。

## 推奨モデル（暫定）

**実音声の比較の第1候補は `gemini-3.5-flash-lite`（`minimal`）。** 反例では差が出ず、同じ根拠に約3秒早く反応し、遅延の裾も短い（合図の時機に直接効く）。弱点は V4 で、途中の申し出を出さず、訂正の後に誤った NEW を1回出した。3.8-flash は V4 が良く、V2 を2回とも申し出なかった。**n が小さいので確定しない。実音声でも両方を流して決める。**

| C3b | 両モデルとも誤った合図を避けられる | — |
| V4（3.8-flash） | 1段で避けられたのは2回中1回。もう1回は次が KEEP で、その次に撤回 | — |
| V1、V2、H1 | 妥当と仮定した合図が遅れる | 約 4.5〜8.3 秒 |

- 版 v1 の C2 では次の判定が KEEP で、その次で撤回だったので、1段の待ちでは足りなかった（2段なら 13 秒前後）。
- 判定の間隔がそのまま遅れになるので、LLM の持続確認は重い。v2 では C2 の候補自体が出なくなった。
- **実 ASR で安定テキストの書き換えがどれだけ起きるかを見て再判断する**（収録スクリプトが `rewrites_of_stable_text` を記録する）。書き換えが多ければ、LLM を呼ばない「根拠が安定になってから一定時間」の待ちを先に試す。値は Jarvis から流用しない。

## 実装上の解釈（統括と C、E、G への申し送り）

1. **安定テキストの定義。** 実測の `long` では 0.9 の範囲が revision ごとに伸び縮みする（文字数 0→10→9→0→24→0→28→35→34→28→42→28。`provider_probe/out/` の2本。文字は変わらない）。最新の revision だけを見ると、根拠が毎秒のように消える。そこで「一度 0.9 になった範囲は、最新の全文がその接頭部を保つ間は安定」とした（`transcript_view.ts` の `high_water`。比較用に `literal` あり）。0.01 の部分は安定に入らない。
2. **interim の末尾の「。」は文末ではない。** 0.9 の瞬間の結果には必ず付く。起動の判定と LLM への入力から除いた。
3. **起動の条件は policy に置けなかった。** 契約の `initiative` 節が strict なので `monitor.ts` の `DEFAULT_TRIGGER` に置いた。統括経由で契約に足すのがよい。**→ 第3部で解消**（`policy.initiative.trigger` に置いた。値は【未検証の暫定値】）。
4. **`policy.ja.json` の【暫定】値:** `max_new_stable_chars_since_input` 60、`max_result_age_ms` 8000（3.8-flash の p95 以上。flash-lite に決めたら 4000 程度へ下げる）、`max_requests_per_session` 200。いずれも実測で決めた値ではない。
5. **撤回の検証。** `withdraw_evidence_span` を出力に足し、候補の根拠より後ろの発話であることをコードで確かめる。`WITHDRAW` は鮮度で棄却しない（安全側の判定なので）。
6. **E2a、E2 までの代役。** `candidate.state_changed` の発行と、活動中の候補があるときの `NEW` の棄却を `monitor.ts` が行っている。移管のときに外す。**→ 第3部で解消**（どちらも E2a の `CandidateLedger` へ移した。monitor は `initiative.decision` と `initiative.discarded` だけを出す）。
7. **試験の場所。** ルートの vitest は `apps/*/test/` しか見ないが、持ち物の外なので `__tests__/` に置いた。`npx vitest run --config tools/initiative_spike/vitest.config.ts` で実行する。ルートの `include` に足すか、移管時に移す。
8. **Gemini の実装の差し替え。** `tools/initiative_spike/lib/gemini_thin.ts` は `LlmProvider` の形で、`run_replay.ts` の `makeProvider` だけを変えれば D の実装へ替えられる。

## 未検証の点

- **実音声、実 ASR、人の評価は全部これから。** 手書きの素材は話速が一定で、認識の誤りと区間の切れ方が現実と違う。形は短い1サンプルに寄せただけで、自然な話し方の安定テキストの遅れは未測定。
- 過剰適合の検査は完全ではない。H1 と H2 は調整に使っていないが、台本もプロンプトも同じ作者（Claude）が書いたので盲検ではない。v2 の「手続きの抜け」は H1 を知った上で書いた。「足りない」の例は C2 に由来する。
- 非決定性の評価ができていない（各 n=1〜2）。
- コードの既定の起動条件（24／12 文字）は未検証。話の後に届く `NEW` の扱いは第3部で決めた（E2a が保留し、人が再開したら照合し直して候補にし、再開しないまま通常応答が始まったら棄てる。`docs/known_gaps.md` §9）。E3 の通常応答との調停は残る。
- C5 は G3 の対象で、今回は流していない。
- Windows の録音アプリの画面と出力の形式は確認していない（24bit と 32bit 浮動小数の WAV は試験で通した）。
- 費用は集計していない（トークン数は `cost.usage` に記録）。

# 第3部: 本実装への移管（レーン G、波2）と関門 G2 の準備

**関門 G2 は未通過。** 下の結果は手書きの逐次 ASR（`fixtures/initiative/handwritten/`、実 ASR ではない）を本実装の経路で流した予備の再実行で、G2 に必要な実音声、実 ASR、研究者の3列の評価はまだない。

## 経路

- `cognition/initiative/monitor.ts`（G）→ E2a の `CandidateLedger.applyModelDecision`。NONE、NEW、KEEP、REVISE、WITHDRAW の全部が E2a を通る。候補の状態、採番、`candidate.state_changed`、`candidate.rejected`、未再生の PCM の破棄（D の `discardCandidate`）は E2a。G は `initiative.decision` と `initiative.discarded` だけを出す。E2a の拒否は `initiative.discarded` に `e2a_rejected:<reason>` として写す。
- `llm.request`、`llm.response`、`cost.usage` は D の Gemini プロバイダが出す。スパイクの monitor が出していた3つ（`cost.usage` の `tokens` 単位を含む）は消した（二重計上の解消）。
- セッション（`session/session.ts`）とリプレイ（`tools/initiative_spike/run_replay.ts`）は同じ `session/initiative_wiring.ts` を通る。STT の結果で増分起動、tick で `observeUserFloor`・`tick`（期限）・`poll`（失敗後の待ちの明け）、`advance_segment` で `onSegmentChanged`、通常応答の開始で `onNormalResponseStarted`、候補の発話の終わりで `finishSpeech`（波2では候補を話さないので通常は呼ばれない）。
- 判定の LLM は応答と別のインスタンス（`INITIATIVE_GEMINI_MODEL`、既定 `gemini-3.5-flash-lite`、思考 `minimal`、時間切れは `max_result_age_ms`、出力上限 4096）。条件は `INITIATIVE_CONDITIONS`（既定は ja で3条件とも、`none` で停止）。
- 判定の失敗（429、時間切れ、不正な出力）は候補を作らず、理由を `initiative.discarded` に残し、次の起動を待たせる（2秒から倍、上限30秒。【未検証の暫定値】、`DEFAULT_FAILURE_BACKOFF`）。
- **波2では候補を作って記録と研究者画面に出すだけ。** TurnManager にも D にも渡さず、候補の TTS も作らない。

## 再実行の方法

```bash
bash tools/initiative_spike/run.sh replay --asr handwritten --scenarios C1,C2,C3a,C3b,C4,C6,V1,V2,V3,V4,H1,H2 \
  --models gemini-3.5-flash-lite:minimal --label <名前> --ledger call_ledger.g2_prep --max-calls 100 \
  --min-new-chars 40 --boundary-chars none --yes
bash tools/initiative_spike/run.sh report --label <名前>
```

起動の条件はスパイク（`p2_v2_tune`）に合わせた 40 文字・文の区切りなし。リプレイは記録を流している間を「人が話している」、流し終えた後を「黙った」として E2a へ伝える（VAP がないので近似）。
